# X Tweet Local Backup

中文｜ [English ↓](#english)

在浏览器里正常发帖、回复、引用时，自动把内容存到本地。纯本地
没有抓dom也没有使用直连账号api
它不是导出工具，是持续记录：你在 x.com 发的每一条，扩展从页面本来就在收发的网络响应里读一份，存进扩展自己的 IndexedDB。

## 它不做什么

- 不自动发帖、回复、点赞、关注、转发。没有任何自动化操作。
- 
- 发起任何自己的网络请求——唯一例外是你主动开启并授权后的媒体下载（`pbs.twimg.com` / `video.twimg.com`）。

## 手机发的帖也能补回来

1.0等早期版本只有在这个浏览器里发布的推文才会被记录，手机 App 发的一条都看不到。

现在打开你自己的主页往下滑，X 会去拉你的时间线——那个响应里就是你的推文，跟从哪台设备发的无关。扩展读它，只保留作者 ID 是自己账号的行，不额外发请求。

测试是一次扫描补回 24 条，其中 8 条藏在线程模块里——只读最明显的路径会漏掉三分之一。往下滑会拉取到更多的数据进行补录

主页的「回复」栏同理，默认关闭（一次可能新增很多行）。

6. 正常发一条推文，然后点扩展图标

> 重载或更新扩展后，已经打开的 x.com 页面同样需要刷新一次。

## 关注和粉丝名单（可选，默认关闭）

**为什么要有这个**：X 封号或锁号之后，关注和粉丝列表就再也打不开了；官方数据归档里**确实有**这两个列表，但**只能在还能登录的时候申请下载**。所以这份数据只在你还进得去的时候拿得到，之后窗口就关了。

打开设置里的「记录关注和粉丝名单」，然后在**自己的主页**打开「关注」或「粉丝」往下滑 —— 滚到哪记到哪，扩展只是读页面本来就收到的响应，从不自己发请求。

- **它记的是「见过谁」，永远不记「谁不在了」。** 分不清"他取关了"和"我这次没滚到"，所以干脆不写 —— 不写就不会错。名单里没有的人，只代表你还没滚到那里
- **以数字 ID 为准**，不以用户名为准。用户名会改，改过名的人会自动合并成同一行
- **只在你自己的名单里抓。** 请求里带着 `userId`，只有它属于扩展见过的你自己的账号时才记录 —— 翻别人的关注列表什么都不会存
- **全新安装需要先发一条帖**：在扩展见过你发帖之前，它不知道哪个账号是你的，这时设置里会写明"还没生效"
- 名单**只在标签页或手机里能看**（弹窗太小，装不下第二个列表）。导出的 ZIP 里多一个 `CONNECTIONS.csv`，用表格软件直接打开

## 数据存在哪里

在**扩展自己的 IndexedDB** 里，跟着浏览器配置文件走。

**清理浏览器数据、卸载扩展、删除配置文件，都会让它消失且无法恢复。** 请定期手动导出：

- **导出 JSON** —— 纯文本
- **导出归档 ZIP** —— 包含全部已缓存的媒体文件

## 已知边界

- 发布时页面必须是开着的，否则那一条不会被当场记录（其他设备发的事后可以补录）
- 时间线补录只覆盖主页的「帖子」和「回复」两栏；**关注和粉丝名单要单独打开开关**，并且需要你手动打开那个页面往下滑
- 归档里的正文**保持原样**，t.co 短链不会改写成真实地址；真实地址单独存在 `entities.urls[].expandedUrl`，显示在卡片下方的「链接指向」里

# English

A personal, **local-only** archive for the posts and replies you publish on x.com.

It observes the network responses your browser *already* receives when you post,
and stores the result in the extension's own IndexedDB. Nothing is ever uploaded.

## What it does NOT do

- No automatic posting, replying, liking, following or retweeting.
- No simulated clicks, typing, or keyboard events.
- No DOM scraping: no `querySelector`, no `MutationObserver`, no reading the
  composer's textarea. Tweet content comes only from the network response.
- No network requests of its own except the optional media download to
  `pbs.twimg.com` / `video.twimg.com`, and only after you grant it.
- No cookies, tokens, `auth_token`, `ct0`, `Authorization` or CSRF values are
  read, stored or exported — not even in the debug panel.

## Install

1. Open `chrome://extensions`.
2. Enable **Developer mode** (top right).
3. Click **Load unpacked** and select this folder.
4. Open or reload `https://x.com` so the content scripts are injected.
5. Post a tweet normally, then click the extension icon.

## Files

| File | World | Role |
|---|---|---|
| `manifest.json` | — | MV3 manifest, two content script entries (MAIN + ISOLATED) |
| `inject.js` | MAIN | Hooks **`window.fetch` and `XMLHttpRequest`**, parses successful CreateTweet responses |
| `content.js` | ISOLATED | Validates page→extension messages, relays to the service worker |
| `background.js` | Service worker | Trust boundary + the only writer to IndexedDB |
| `db.js` | Module | IndexedDB schema, upsert, paging, search, export cursor |
| `settings.js` | Module | Settings + diagnostics counters in `chrome.storage.local` |
| `media-cache.js` | Module | Optional media blob cache (off by default) |
| `zip.js` | Module | Minimal ZIP writer (STORE, no dependencies) for the media archive |
| `popup.html/.css/.js` | Extension page | List, search, export, settings, diagnostics |
| `icons/` | — | 16 / 32 / 48 / 128 px. Generated by `make-icons.mjs` (kept outside this folder); the design is an original mark, deliberately not X's logo |

## Data flow

```
x.com page
  └─ inject.js (MAIN world)      hooks fetch AND XMLHttpRequest, detached observation
       └─ window.postMessage     already-parsed, credential-free JSON
            └─ content.js (ISOLATED)   shape + size + token validation
                 └─ chrome.runtime.sendMessage
                      └─ background.js (service worker)  re-validate, whitelist
                           └─ IndexedDB  (extension origin)
popup.html/js  ──reads──>  same IndexedDB  +  stats/settings via background.js
```

### Response envelopes do NOT follow the operation name

Verified against live traffic (2026-09):

| Operation | URL | Response envelope |
|---|---|---|
| `CreateTweet` | `/i/api/graphql/<queryId>/CreateTweet` | `data.create_tweet` |
| `CreateNoteTweet` | `/i/api/graphql/<queryId>/CreateNoteTweet` | `data.notetweet_create` |
| `CreateRetweet` | `/i/api/graphql/<queryId>/CreateRetweet` | `data.create_retweet` → `retweet_results.result` |
| `DeleteTweet` | `/i/api/graphql/<queryId>/DeleteTweet` | nothing readable — see below |

Note the second one: the operation is `CreateNoteTweet` but the envelope key is
`notetweet_create` — neither the operation name nor `create_note_tweet`. Long-form
posts are routed to that separate operation, so a parser that only knows
`create_tweet` silently drops every long post. `CREATE_RESULT_KEYS` in `inject.js`
is the single list that handles this, and when none of its keys match, the
failure message names the keys X actually sent.

### Which transport x.com actually uses

Verified against live traffic (2026-09):

```
POST https://x.com/i/api/graphql/<queryId>/CreateTweet   via XMLHttpRequest
```

**Publishing goes over XHR, not fetch.** An earlier version of this extension
hooked only `window.fetch` and captured nothing at all. Both transports are now
hooked, and every record records which one it arrived on in
`source.capturedVia` — so the next time X changes transport, the archive shows
it instead of silently going empty.

### Retweets, edits and polls are all `CreateTweet`

Neither edit nor delete is a GraphQL operation of its own. Both are ordinary
`CreateTweet` / `CreateNoteTweet` calls that differ only in their **request
variables**, which is the only place the distinguishing information exists.

| Feature | How to tell, from the request | Effect |
|---|---|---|
| Edit | `variables.edit_options.previous_tweet_id` | new record: `isEdit`, `editedFrom`, `editTweetIds`, `editInitialTweetId`, `editsRemaining` |
| Poll | `variables.card_uri`, confirmed by a card named `poll*` | `isPoll`, `poll.*` |
| Delete | operation is `DeleteTweet`; `variables.tweet_id` | **marks** the existing record: `deletedAt` |

These variable names were read out of X's own client bundle — the code that
builds the CreateTweet payload, and the code that parses the response back. They
are not guesses, and they are not the sort of thing that rotates (unlike
`queryId`).

**An edit returns a NEW tweet id.** Each version is archived as its own row,
chained by `editedFrom`, and the previous row is stamped with `supersededBy`
so the list can show "已有新版本" instead of two unrelated-looking records.

### Retweets are deliberately not archived

`CreateRetweet` is not matched. This used to be an opt-in feature and was
removed, because it could never produce anything worth keeping:

- the response contains **only the new retweet's own id** — no text, no author,
  no timestamp, no media;
- the original tweet's id exists *only* in the request body;
- X does not re-fetch the original either, so it cannot be picked up passively.

What you got was an empty row pointing at somebody else's post. Do not re-add
it without a way to capture the original — a content-free record in a personal
archive is worse than no record.

Records archived while the feature existed still carry `isRetweet` and
`retweetedTweetId`, and the list still renders their badge; new records always
have both unset.

### Deleting a post marks the record; it never removes it

When you delete one of your own posts on X, `DeleteTweet` fires, and the
archive marks the row it already holds with `deletedAt` and shows a `已删除`
badge. **The record is kept.**

That is the whole point of the feature. `DeleteTweet` is the one mutation whose
response says nothing: X's own client calls it as

```js
destroy(e) { return t.graphQL(DeleteTweet, { tweet_id: e.id }) }
```

with **no response selector** — unlike retweet (`create_retweet`) or bookmark
(`tweet_bookmark_put`), there is no field being checked, and the string
`delete_tweet` appears nowhere in the client bundles. So success is exactly what
it is for X: a 2xx response carrying no errors. The tweet id can only come from
the request.

A deletion does **two separate things**, and the second one is what makes
multi-machine archives work:

1. **It always records the event**, in its own `deletions` store — `{id,
   deletedAt}` and nothing else. This happens even when this machine never
   archived the tweet, which is the normal case when you post on one computer
   and delete from another. The merge tool reads this list and applies each
   deletion to whichever machine did archive the tweet.
2. **It marks the local record**, when there is one, which is what the list
   and the `已删除` badge show.

The event log is kept apart from the tweets on purpose. A deletion has to be
recordable with no tweet to attach it to, and inventing a content-free row in
the tweet list would put an entry in the archive with no text, no author and no
media.

The first deletion timestamp wins — a tweet can only be deleted once, and
re-observing a deletion does not rewrite anything.

**Removing a backup removes everything about that id**, tombstone included.
Otherwise a merge would silently re-mark a tweet you had deliberately removed
from the archive. This applies to single-record deletion, to purging the
`已删除` category, and to 清空全部备份.

Un-retweeting (`DeleteRetweet`) is **not** handled, and now has nothing to
handle: retweets are not archived at all, so there is no row for it to mark.

### What is verified about polls, and what is not

Verified from X's client bundle: the poll card names, the exact test X applies
to decide a card is a poll, and the binding keys the choices live under.

That test is a verbatim port of X's own `isPollCard()`, including its two
awkward details — the prefix is **case-sensitive**, and the image-poll card is
registered under an id-prefixed name whose *second* colon-separated half is the
one that matters:

```js
"poll2choice_text_only"                   // must start with "poll"
"1906814671912599552:poll_choice_images"  // second part must start with "poll"
```

Choices are read from `choice1_label` … `choice4_label`, with
`end_datetime_utc` and `counts_are_final` recorded alongside. `binding_values`
is accepted in both shapes X uses — the raw GraphQL array of `{key, value}` and
the client's normalised `key → value` map.

**Not verified against a live post:** whether the CreateTweet *response*
actually inlines the poll card. That could not be checked without publishing a
poll, and this extension does not publish anything. So both cases are handled
and reported honestly rather than assumed:

- card present → choices are archived;
- card absent → the record still carries `poll.cardUri` and reports
  `choicesFromResponse: false`, and the popup says the choices were not
  returned instead of drawing an empty box.

A `card_uri` on its own is **never** treated as proof of a poll: link previews,
players and product cards attach one too. Such a post gets a neutral
`附带卡片` badge and no type claim.

## Verifying it works

1. Open x.com, press F12 → Console, and filter for `X Tweet Backup`.
2. Turn on **调试模式** in the popup: the diagnostics panel appears and the page
   logs become verbose.
3. Post a tweet. Expected: `本页 CreateTweet 观察数` +1, `本页成功解析数` +1,
   `IndexedDB 写入成功` +1, and the record appears in the list.
4. Try a reply, a quote tweet, an image, multiple images, a video, a GIF and a
   long-form post — each should produce one record.
5. Confirm the original post still behaves normally: the page must keep working
   exactly as before, and the tweet must publish even if you disable the
   extension mid-flight.

If `本页 CreateTweet 观察数` stays 0 while posting, the hook is not seeing the
request — see *Known limitations*.

## Media: two separate things

"Capturing media" means two different things here, and they are stored and
exported separately.

**1. Media metadata — always captured.** Every post stores, per attachment: id,
type, `media_url_https`, a thumbnail URL, width/height, alt text, and video
`variants` / duration / aspect ratio. This lives inside the tweet record, so it
is included in the JSON export.

**2. Media bytes — off by default.** The actual files are only downloaded if you
switch on **缓存媒体文件到本地** in the popup, which asks for `pbs.twimg.com` and
`video.twimg.com` permission. Downloads are asynchronous, never block the text
record, and a failure never affects it. Caps: 15 MB per file, 300 MB total.

In the popup every thumbnail carries a dot saying which of the two you are
looking at:

| Dot | Meaning |
|---|---|
| amber | loaded from the network — **only the URL is archived** |
| green | the file itself is cached locally |

### The two exports

| Button | Contents | Use it for |
|---|---|---|
| **导出 JSON** | every archived post: text, timestamps, author, reply/quote links, entities, media metadata, metrics; plus the `deletions` list | frequent, lightweight backup. Small, greppable, diffable. Always complete for text regardless of whether media was cached. |
| **导出归档 ZIP** | `tweets.json` **+** every cached media file **+** `MEDIA-INDEX.txt` / `.json` | one self-contained portable archive — migration, long-term storage, handing the whole thing to another tool |

The archive unpacks to exactly this, with no tooling required:

```
x-tweet-backup-archive-YYYY-MM-DD.zip
├── tweets.json          same document the JSON export produces
├── MEDIA-INDEX.txt      human-readable table
├── MEDIA-INDEX.json     machine-readable join table
└── media/
    └── <tweetId>_<mediaId>.<ext>
```

The join is stated twice on purpose: the filename contains both ids, and
`MEDIA-INDEX.json` spells the mapping out, so a reader years from now does not
have to reverse-engineer the naming rule.

Files are stored uncompressed (STORE) because JPEG/PNG/MP4 are already
compressed — deflating them again would cost CPU and save nothing. The writer
lives in `zip.js` and has no dependencies.

Two consequences worth knowing:

- **The JSON never contains image data.** Base64-ing hundreds of megabytes into
  one document would inflate it ~33% and force a full load just to read a single
  line; the JSON stays a metadata format, and the bytes travel in the ZIP.
- **The ZIP only contains media that was cached.** Anything archived before you
  enabled caching keeps its URL in `tweets.json` but has no file in `media/`.
  There is no backfill in this version, and the archive's index reports how many
  records were skipped for that reason.

## The export carries deletions separately

`tweets.json` has two arrays, not one:

```json
{
  "schemaVersion": 3,
  "tweets":    [ /* full records */ ],
  "deletions": [ { "id": "…", "deletedAt": "2026-09-23T08:05:19.840Z" } ]
}
```

A merge should union `tweets` by `id` (the id is the tweet id, so it is unique
across machines), then apply every entry in `deletions` — including the ones
whose id is not in the merged tweet set, because those are exactly the
deletions observed on a machine that never had the tweet.

Two things a merge has to get right beyond a plain union:

- **`editedFrom` is the authority for edit chains, not `supersededBy`.**
  `supersededBy` is written locally when the later version is archived *on the
  same machine*. If version 1 was captured on machine A and version 2 on
  machine B, neither copy has it. After merging, recompute `supersededBy` from
  the `editedFrom` links rather than trusting the field as merged.
- **`capturedAt` and `firstCapturedAt` may differ per machine.** Keep the
  earliest `capturedAt` so list ordering stays stable.

## The follow roster (opt-in, off by default)

A third array may appear, **after `deletions`**:

```json
{
  "connections": [
    {
      "list": "following",
      "userId": "2090325165590876160",
      "screenName": "hoshino_Fuji",
      "screenNameLower": "hoshino_fuji",
      "name": "听风藤",
      "bio": "…",
      "followersCount": 662,
      "followingCount": 354,
      "tweetCount": 199,
      "firstSeenAt": "2026-09-20T10:00:00.000Z",
      "lastSeenAt": "2026-09-21T10:00:00.000Z",
      "ownerIds": ["2032037309219315712"],
      "source": { "operationName": "Following", "capturedVia": "xhr" },
      "schemaVersion": 3
    }
  ]
}
```

It is **omitted entirely when empty**, so an archive from someone who never
switched the feature on is byte-for-byte what earlier versions wrote. The field
is `tweetCount`, never `tweets` — the standalone reader locates the tweet array
by scanning the raw bytes for that key, and a second one would be found first.

**This is a roster, not a change log.** A person is in the array because they
were *seen*, and absence means only that the page was not scrolled that far. X
gives no way to tell "they left" apart from "I did not look", so no removal is
ever recorded, and a merge should union these rows by `[list, userId]` and take
the newest `lastSeenAt`.

`userId` is the identity and `screenName` is a label that can change. Two
archives merged on the handle would split one person across two rows — or, worse,
merge two people if a released handle was taken.

**Nothing is captured from anyone else's list.** A `Following` response does not
say whose list it is, so the extension checks the `userId` the page itself put in
the request against the accounts it has watched publish from. Browsing somebody
else's followers stores nothing at all.

The ZIP adds `CONNECTIONS.csv` when the roster is non-empty — the same rows, with
stable English headers, for a spreadsheet.

## Link expansions are archived, because t.co is not yours

X rewrites every link in a post to a `t.co` shortlink and keeps the real
destination only in `entities.urls[].expanded_url`. That shortlink resolves
through X's own service, so the moment it stops resolving, the archived text no
longer says where it pointed — and there is no way to recover it afterwards.

So the record carries both, and the **text is never rewritten**: what is
archived is what was published, with the shortlink still in place.

```json
"text": "look at this https://t.co/zAoH546pDp",
"entities": {
  "urls": [
    { "url": "https://t.co/zAoH546pDp",
      "expandedUrl": "https://example.com/a/very/long/path",
      "displayUrl": "example.com/a/very/…" }
  ],
  "hashtags": ["cool"],
  "mentions": [{ "id": "555", "screenName": "bob", "name": "Bob" }]
}
```

Long-form posts keep the same three lists under `entity_set` rather than
`legacy.entities`; both are read. `lang` (X's own `legacy.lang`) is archived too.

**A reader UI must never make the `t.co` link in `text` clickable.** That
shortlink resolves through X's own redirect service, so following it tells
Twitter that this archive was opened and which link was clicked. Render
`expandedUrl` instead — it points straight at the real host. The two are stored
separately for exactly this reason: `text` is what was published, `expandedUrl`
is where it actually goes, and only the second one is safe to follow.

A record always has `entities` as an object with three arrays — never `null` —
so a reader can index into it without guarding. **Records captured before schema
v2 have no `entities` and no `lang`**; add `schemaVersion: 2` to the check if you
need to know which you are looking at.

Link expansion is the one place where a sanitizer rule differs from media URLs:
a link you typed can point anywhere, so the **host is not constrained** — only
the scheme is. `javascript:` and `data:` URLs are dropped at the trust boundary
so a future reader UI can never be handed one.

## Timestamps are UTC (this is deliberate)

Every timestamp in the archive — `createdAt`, `capturedAt`, `exportedAt` — is
**UTC**, in ISO 8601 with a trailing `Z`. `createdAtRaw` preserves X's original
string, which is also UTC (`+0000`).

Three reasons this is not a bug:

1. `capturedAt` is an IndexedDB index and pagination compares it as a **string**
   (`IDBKeyRange.upperBound`). UTC ISO-8601 strings sort lexicographically in
   chronological order; local times carrying an offset would not.
2. ISO 8601 + `Z` is an unambiguous absolute instant.
3. It stays correct across timezone and daylight-saving changes.

The **popup converts to your local time automatically** (`Intl.DateTimeFormat`).
Only the exported JSON shows UTC, because that file is a data format rather than
a reading view. To read a timestamp by hand, add your offset: for UTC+08:00,
`2026-09-22T21:44:25Z` is `2026-09-23 05:44:25` local.

### The export states the timezone once, instead of converting every timestamp

Rather than repeat a converted local time beside each of thousands of
timestamps — which would also bake in the zone you happened to be in when you
exported, and be wrong later — the JSON says it once at the top:

```json
"timezone": {
  "name": "Asia/Shanghai",
  "offsetMinutes": 480,
  "note": "时间戳均为 UTC。本地时间 = UTC + offsetMinutes 分钟。"
}
```

Any reader can then render every timestamp in that zone, and the stored values
stay unambiguous instants either way.

## Known limitations

- **This extension can only be as reliable as the current X web fetch /
  CreateTweet implementation.** If X changes its front-end networking, moves to a
  different transport, replaces `window.fetch`, or reshapes the GraphQL response,
  capture can stop working.
- Both hooked globals are shared with the page. X (or another extension) may
  replace `window.fetch` or `XMLHttpRequest.prototype`; the extension detects
  this per transport and deliberately **does not** fight the page to reinstall
  itself. The diagnostics panel reports each transport separately, so losing
  `fetch` does not misreport the XHR hook as dead.
- Requests that do not pass through the page's `fetch` or `XMLHttpRequest` are
  not observed. In particular X issues some calls (`timeline.json`,
  `live_pipeline`) from **its own service worker**, which no page-level hook can
  see. Publishing currently does not use that path.

### Reloading the extension requires refreshing x.com

**After you reload or update the extension, every already-open x.com tab must be
refreshed (F5) before it can back anything up again.**

Chrome tears down the extension APIs of content scripts that were injected
before a reload. The page keeps working normally, `inject.js` keeps detecting
posts — and every capture is dropped on the floor with nothing reaching
IndexedDB. Only a page refresh injects a fresh content script.

The extension now detects this and says so, loudly, in the page console
(`备份通道已失效…请刷新本页面（F5）`), and the popup carries the same warning.
The data published during that window cannot be recovered afterwards.

### What gets archived — and what silently does not

The extension only observes network traffic inside **this Chrome profile on this
computer**. Anything you publish anywhere else is invisible to it:

| Where you post | Archived? |
|---|---|
| x.com in this Chrome profile | **yes** |
| x.com in another browser, or another Chrome profile | no |
| The X mobile app (iOS / Android) | no |
| x.com in a browser on your phone | no |
| A third-party client | no |

Critically, **there is no error, no warning and no gap marker when a post is
missed** — the extension simply never sees it. So treat the archive as
*"everything I posted from this browser"*, never as *"everything I posted"*.
If you post from your phone regularly, the archive will have silent gaps.

Closing that gap would require actively fetching your own timeline back from X
(a backfill feature). This version deliberately does not do that: it records
only what the page already received, and never issues requests of its own to
x.com.
- Text, media, and reply metadata all come from the network response, never from
  the DOM. If X stops returning a field, the request-side fallback is used where
  one exists, otherwise the field is stored as null rather than guessed.
- **Edits are captured as new versions, not as in-place changes.** An edit is a
  `CreateTweet` carrying `previous_tweet_id` and returns a *new* tweet id, so the
  archive keeps every version as its own row, chained by `editedFrom`, with the
  older row marked `supersededBy`. The original wording is therefore never lost —
  which is the point of an archive — but the list will show one row per edit
  rather than one row per tweet.
- An edit made to a tweet that predates the extension has no archived previous
  version, so `editedFrom` points at an id that is not in the archive. The link
  still works on x.com; nothing is marked `supersededBy`.
- A media-only post is stored with `text: ""`, not with the `t.co` placeholder
  X puts in `full_text`. The real media URL is kept in `media[].url`.
- The `queryId` in the GraphQL URL rotates frequently — the extension never
  hardcodes it, matching on the `CreateTweet` operation name instead.
- Images are only archived as URLs unless you enable media caching. A URL is not
  the media itself, and twimg URLs can expire or be removed.
- Deleting a tweet on X does not delete your local copy. That is intentional.
- Search covers text, tweet id and author name. It scans with an IndexedDB
  cursor, so a very large archive makes each search page slower.
- Pagination resumes on an exclusive `capturedAt` bound; two tweets captured in
  the same millisecond could theoretically be skipped.
- Very large JSON exports are assembled in memory and may be slow.
- **Data loss is possible.** Uninstalling the extension, deleting your Chrome
  profile, or clearing extension data destroys the archive. Export JSON
  regularly as a second layer of backup.
- Not a security boundary: page scripts share the realm with `inject.js` and
  could forge messages. The service worker re-validates and whitelists
  everything, so the worst case is a junk record, never code execution or
  credential exposure.

## If capture stops working, look here first

| Symptom | File | What to inspect |
|---|---|---|
| Nothing observed at all | `inject.js` | **first check whether X switched transport** (Network panel: fetch or XHR?), then `installHook()`, `installXhrHook()`, `CREATE_OPERATIONS`, `analyzeRequestUrl()` |
| Diagnostics show one transport 已被页面覆盖 | `inject.js` | `startIntegrityCheck()` / `hookHealth` — expected when another extension patches the same global |
| Observed but not parsed | `inject.js` | `CREATE_RESULT_KEYS` first (see below), then `collectResultCandidates()`, `TEXT_PATHS`, `extractTweetId()` |
| Diagnostics say `no tweet result candidate (data keys: ...)` | `inject.js` | the error names the reply envelope X actually sent — add that key to `CREATE_RESULT_KEYS` |
| Text is wrong/truncated | `inject.js` | `TEXT_PATHS` order (note_tweet must stay first) |
| Long posts missing | `inject.js` | `CREATE_OPERATIONS` (X may use a separate long-form operation) |
| Media missing | `inject.js` | `MEDIA_PATHS`, `normalizeMedia()` |
| Reply/quote fields missing | `inject.js` | `buildTweetRecord()`, the `variables` fallbacks |
| Records rejected at storage | `background.js` | `sanitizeRecord()` and its helpers |
| Popup list/search wrong | `db.js` | `queryTweets()`, index names |
| Media cache failing | `media-cache.js` | `MEDIA_HOSTS`, `pickBestSource()` |

Turn on **调试模式** first: `最近一次失败原因` in the diagnostics panel usually
names the exact stage that rejected the response.
